# Emite Fácil current API contract audit

Audited 2026-10-17 from local source `D:/Proyectos Personales/backend-emite-facil`. Source application was not modified. No environment files, credentials, remote endpoints, or internet sources were read. This is static inspection, not a claim that integration or e2e tests were executed.

## Authority and API base

Controllers/services are the authority for runtime behavior. `contracts/openapi.yaml` is OpenAPI 3.1, API version 0.15.0, with `servers: [{url: /api/v1}]`. Its paths omit that prefix; Java controllers include it. Thus the actual current-tenant endpoint is `GET /api/v1/tenants/current`. Configure an adapter with an origin (or proxy deployment root), and append `/api/v1` exactly once. Never append an upstream `statusUrl` to an already-prefixed base without normalizing it.

Inspected controllers: `tenancy/TenantController`, `taxpayer/{Taxpayer,Establishment,EmissionPoint}Controller`, `catalog/{Catalog,Customer,Product}Controller`, `billing/{Invoice,Document}Controller`, `storage/ArtifactController`, `webhook/WebhookController`, all under `src/main/java/com/example/einvoice/`. Supporting services, repositories and resolvers named below were inspected too. Supporting tests: `apikey/ApiKeyAuthenticationIT`, `billing/{InvoiceApiIT,InvoiceIdempotencyIT,InvoiceReissueIT}`, storage artifact tests, `e2e/tests/{api-keys,integraciones}.spec.ts`, and `e2e/support/webhook.ts`.

## Authentication and permissions

Send only `X-Api-Key: <raw API key>`, never `Authorization` together with it. Both headers present yields HTTP 400 `CREDENTIALS_AMBIGUOUS` even when one value is empty. Absent, blank, malformed, invalid or revoked key yields 401 `UNAUTHENTICATED`; suspended tenant or a creator who lost active billing membership also invalidates it. Authentication DB failures yield 503 `INTERNAL_ERROR`, not 401. Key format generated by the app is `efk_` + 12 alphanumeric characters + `_` + 43 base64url characters; treat it as an opaque secret and do not log it.

`TenantAccessResolver` fixes the active tenant to the key's tenant and role to `BILLER`, regardless of creator's higher role. No tenant ID in JSON. `X-Tenant-Id` is optional; if nonblank it must be the key's UUID (400 `TENANT_HEADER_INVALID` for malformed value, 403 `TENANT_FORBIDDEN` for another UUID).

Key-permitted reads needed by HCX: current tenant, taxpayers and individual taxpayer, establishments, emission points, all catalogs, customers, products, documents, artifacts. These endpoints resolve `TenantAccess` without demanding a configuration-writing role. Key can create customers, invoices, and products. Product creation is an explicit API-key exception in `TenantAccess.requireProductCreation()`; a human BILLER cannot create products. No key can configure issuer/establishment/point/certificate/API keys. Every webhook service operation, including list subscriptions, list deliveries, test, retry, and secret rotation, calls `requireWrite()` (OWNER/ADMIN); key gets 403 `ROLE_FORBIDDEN`. Creating/listing tenants or accessing person-only auth endpoints gets 403 `API_KEY_NOT_ALLOWED`.

Consequently HCX must receive webhook URL registration and its one-time secret through an independently authorized OWNER/ADMIN setup; connectivity validation using the API key must not depend on webhook management endpoints. Current tenant is `{id,name,status,role}` with status ACTIVE/SUSPENDED and key role BILLER.

Actual pagination is `{items: T[], page: number, size: number, total: number}`; never `{data}`, `{content}` or `{totalElements}`. Pages are zero-based, defaults 0/20, permitted page 0..100000 and size 1..100 inclusive (400 `MALFORMED_REQUEST` otherwise). Iterate while `(page + 1) * size < total`; empty `items` is also a safe stop. `q` defaults to empty, is stripped, max 100 characters, no control characters; `%`, `_`, and backslash are literal, not wildcard syntax.

Options chain: taxpayers -> establishments by taxpayer UUID -> points by establishment UUID. Persist/use each entity's UUID for lookup, but issue invoices with the selected taxpayer UUID and the establishment/point **three-digit string codes** (preserve leading zeroes). Points include `enabled`; avoid disabled points. Environments are string `'1'` (test) or `'2'` (production), derived from taxpayer `defaultEnvironment`, not supplied on invoice POST.

Tax-rate codes are strings, not percentage values: e.g. `{taxCode:'2',rateCode:'4',description:'15%',rate:'15.00'}`. Current seeded rates for taxCode 2 are 0->0, 2->12, 3->14, 4->15, 5->5, 6->0 non-taxable, 7->0 exempt, 8->8 differentiated, 10->13. Fetch the catalog rather than treating seeded values as permanent. Product `ivaRateCode` takes the rate code, e.g. `'4'`, not `'15'`.

## Find/create semantics and changed customer data

Customer search matches case-insensitive name contains OR identification-number prefix, ordered by name then UUID. Find an identity by `q=idNumber`, paginate all results, and compare BOTH exact `idType` and exact `idNumber`; the server has no unique-identification lookup route. Customer identity uniqueness is per tenant + idType + idNumber (`customers_identification_key`). Create duplicate -> 409 `CUSTOMER_ALREADY_EXISTS`, not an upsert. On a create race, repeat exact lookup. Required fields: idType exactly two digits, idNumber nonblank <=20, name nonblank <=300. Optional email <=254 and valid email, address <=300, phone <=30. Catalog controls allowed identification type and number pattern (422 `IDENTIFICATION_TYPE_UNKNOWN` / `IDENTIFICATION_INVALID`). Name and optional contact fields are stripped; blank optional contact values become null. Identity fields are not stripped by service.

**There is no customer PUT or PATCH in either Java controller or OpenAPI.** If HCX has a changed name or email for an existing identity, POST cannot refresh it and a duplicate cannot create another version. Invoice POST accepts `customerId` only, no name/email override. `InvoiceService` snapshots the stored customer's name/address/email into the document. Safest adapter behavior is return the exact existing identity together with an explicit mismatch result (or a typed `customer_data_conflict`), and require reconciliation before claiming current data was sent. Do not silently claim that a successful lookup refreshed a name/email. Correct current data cannot be guaranteed until upstream supports an update path or data is corrected upstream. An explicit delivery email override can affect email delivery but does not update the fiscal snapshot.

Product search is case-insensitive name OR SKU contains, ordered name then SKU. Search using `q=sku`, paginate, compare exact SKU; result can contain partial matches. Duplicate create -> 409 `PRODUCT_SKU_TAKEN`; repeat lookup on race. SKU matches `[A-Za-z0-9._-]{1,25}`, name <=300, required string unitPrice, required numeric-string ivaRateCode of 1..4 digits. Unknown rate -> 422 `TAX_RATE_UNKNOWN`. There is no product PUT/PATCH either. Invoice line may override unitPrice but not product description or IVA code; mismatched existing SKU/rate/name is not automatically synchronized. Use deterministic bounded SKUs and keep an HCX mapping.

## Invoice acceptance, idempotency and replacements

`Idempotency-Key` is mandatory, matching `[A-Za-z0-9._:-]{1,100}`; missing/blank -> 400 `IDEMPOTENCY_KEY_REQUIRED`, invalid -> 400 `IDEMPOTENCY_KEY_INVALID`. Scope is tenant + key, not API-key identity. Store a stable key and the exact intended request before submitting; retry that same request/key after timeout, transport failure or retryable server failure. Different parsed DTO content with the same key -> 409 `IDEMPOTENCY_KEY_REUSED`. Hash is SHA-256 of Jackson serialization of the parsed DTO: JSON whitespace/property order do not matter, but don't assume decimal spellings, line order, optional defaults or omitted/defaulted values are interchangeable. Idempotency reservation and invoice creation share a transaction: rejected validation leaves no consumed sequence or idempotency record. Concurrent duplicate calls serialize through the idempotency table. Successful replay returns the original document ID and its current state, still HTTP 202.

Required invoice fields: taxpayerId, establishmentCode (three digits), emissionPointCode (three digits), customerId, 1..500 lines, 1..20 payments. Optional issueDate defaults to current fiscal date (America/Guayaquil), cannot be future or precede the last issued date on the same emission-point sequence (422 INVALID_ISSUE_DATE). An exhausted sequence yields 422 SEQUENCE_EXHAUSTED. Optional currency defaults USD and only USD is accepted. Line requires productId and quantity; unitPrice defaults product price, discount defaults zero. Decimal JSON values are strings: quantity/price up to 12 integer and 6 fractional digits, amount/discount up to 12 integer and 2 fractional digits. Digits and optional dot only; no minus, exponent, commas or surrounding whitespace. Quantity must be positive; service rejects invalid line totals. Responses use six decimal places for quantity/unitPrice, two for amounts/rates. Payments use methodCode and amount and must exactly sum to computed total; validity of a payment method is checked at issueDate.

Accepted response: `{id,state,statusUrl:'/api/v1/documents/{id}'}`. Initially state RESERVED; HTTP 202 is asynchronous acceptance, not SRI authorization. Poll document GET and/or consume authenticated webhooks. Do not assume a Location header or artifact URLs in this response.

Optional `replacesDocumentId` creates a **new** invoice with new UUID, sequence and access key and links both documents. Original state/content do not change. Only same tenant, same taxpayer, original state RETURNED / NOT_AUTHORIZED / XSD_INVALID, once per original. Conflicts: 409 `REPLACED_DOCUMENT_NOT_REJECTED`, `REPLACED_DOCUMENT_OTHER_ISSUER`, `DOCUMENT_ALREADY_REPLACED`; foreign/missing original -> 404. Use a new stable idempotency key for the new attempt. Network replay of the original key returns the original invoice; it does not reissue it.

## Document states and artifact contract

Document states: RESERVED, GENERATED, SIGNED, SENDING, RECEIVED, AUTHORIZED, XSD_INVALID, SIGNATURE_FAILED, RETURNED, NOT_AUTHORIZED. Normal flow is RESERVED -> GENERATED -> SIGNED -> SENDING -> RECEIVED -> AUTHORIZED. SIGNED may wait for transmission enablement; SENDING can represent an uncertain SRI outcome. RETURNED and NOT_AUTHORIZED are fiscal rejections; XSD_INVALID is local XML failure. SIGNATURE_FAILED is a signing failure, not fiscal rejection. There is no document state DELIVERED, ERROR or PROCESSING in this enum (PROCESSING is an authorization-attempt outcome). Authorization number and timestamp are nullable until authorization. Number is `001-001-000000001`; sequence is a nine-digit string and accessKey a 49-digit string.

Artifacts are downloaded at `/api/v1/documents/{id}/artifacts/xml-unsigned`, `xml-signed`, `sri-authorization`, `xml-authorized`, or `ride`. XML media type `application/xml`; RIDE is `application/pdf`. Body is bytes, not JSON/base64, and not a signed URL. `Content-Disposition` is attachment; invoice filename is `factura-{number}-{kind}.xml` or `.pdf`. Unknown kind -> 400 `MALFORMED_REQUEST`; unavailable/not-generated artifact and foreign document both -> 404 `NOT_FOUND`. Authorization can precede PDF generation, so an artifact 404 does not automatically mean invoice failure.

`ETag` is the content SHA-256 in lowercase hex **surrounded by double quotes**, e.g. `"<64 lowercase hex characters>"` (strong ETag, no `W/`). `ArtifactStoreIT` explicitly asserts these surrounding quotes. Keep the original header for conditional requests and optionally strip quotes when comparing a computed digest. Controller declares no explicit conditional-GET behavior; do not require a particular 304 behavior as adapter contract.

## Webhook protocol

`WebhookSigner` generates `whsec_` + standard Base64 of 32 random bytes. Store the raw one-time returned secret unchanged; for HMAC remove exactly the `whsec_` prefix and **Base64-decode** the remainder. Do not use literal secret text or a hash of it as the key. There are no `X-Webhook-*` headers.

Headers: `webhook-id` (event UUID), `webhook-timestamp` (Unix seconds, renewed per delivery attempt), `webhook-signature` (`v1,<standard Base64 HMAC-SHA256>`). Sign exactly the UTF-8 prefix `${id}.${timestamp}.` followed by the original raw request bytes. Verify before JSON parsing/re-serialization using constant-time digest comparison. During rotation multiple signatures are space-separated; accept any valid v1 signature. Timestamp freshness is receiver policy; a five-minute window is a reasonable HCX policy, not a guarantee specified by this server. Deduplicate by tenant + eventId, make state updates idempotent, and fetch GET document to reconcile late events. `document.state` is the event's captured state and may lag the document's current state. Delivery is at least once. A 2xx response acknowledges the webhook.

Document event body has exactly `eventId,eventType,occurredAt,tenantId,document`; nested document is `id,documentType,number,accessKey,state,authorizationNumber,authorizedAt`. No customer PII or amounts, no top-level documentId, no data wrapper, no subscriptionId on document events. Types: `document.received` for RECEIVED; `document.authorized` for AUTHORIZED; `document.rejected` for RETURNED / NOT_AUTHORIZED; `document.delivered` after email send with document state AUTHORIZED. XSD_INVALID does not currently emit document.rejected. `occurredAt` and authorizedAt are UTC ISO timestamps truncated to seconds. Authorization fields are null on non-authorized events. Test event is a separate shape with eventType `webhook.test`, plus `eventId,occurredAt,tenantId,subscriptionId` and **no document**.

## Error classification and retry policy

All application HTTP errors are `application/problem+json` with standard problem fields plus `errorCode`, `correlationId`, and optional `errors:[{field,message}]`. For non-JSON proxy errors retain status and use a sanitized fallback; a malformed 2xx JSON/shape is `invalid_response`, never success. Respect `Retry-After` in seconds on 429 and any positive server-provided value.

| Failure | Classification | Action |
| --- | --- | --- |
| Timeout, DNS/socket abort | transport, retryable | Invoice outcome unknown: replay same body/key; no new invoice attempt |
| HTTP 500/502/503/504 (all other 5xx conservatively) | upstream_unavailable, retryable | Bounded backoff; same invoice key; 503 key verification is not invalid credentials |
| 429 RATE_LIMITED | rate_limit, retryable | Respect Retry-After, bounded backoff |
| 401 UNAUTHENTICATED | authentication, not automatically retryable | Fix/reconnect credential or tenant membership |
| 403 ROLE_FORBIDDEN / TENANT_FORBIDDEN / API_KEY_NOT_ALLOWED | authorization, not retryable | Fix scope/setup; do not try owner-only setup with key |
| 400 VALIDATION_FAILED / MALFORMED_REQUEST / CREDENTIALS_AMBIGUOUS / IDEMPOTENCY_KEY_* | validation, not retryable | Correct request; keep request intent stable across unknown outcomes |
| 422 domain validation | validation, not retryable | Correct data/configuration; examples PAYMENTS_MISMATCH, INVALID_LINE, INVALID_PAYMENT, PAYMENT_METHOD_UNKNOWN, TAX_RATE_UNKNOWN, EMISSION_POINT_DISABLED, INVALID_ISSUE_DATE, UNSUPPORTED_CURRENCY, FINAL_CONSUMER_LIMIT_EXCEEDED, AMOUNT_TOO_LARGE |
| 404 NOT_FOUND | not_found, usually not retryable | Verify mapping/scope; artifact unavailable can be a polling condition |
| 409 CUSTOMER_ALREADY_EXISTS / PRODUCT_SKU_TAKEN | conflict | Recover by exact lookup and compare; not blind POST retry |
| 409 IDEMPOTENCY_KEY_REUSED | conflict, not retryable | Existing key belongs to different intent; investigate, never randomize key to hide conflict |
| Other 409 replacement conflicts | conflict, not retryable | Reconcile linked documents/state |
